# Architecture

MD Reader is an Electron application with a React renderer. The design follows from one rule: **a Markdown file is untrusted input**. Everything that touches the disk, the operating system or the network happens in the main process, behind validation, and the page can only ask for a small, fixed set of things.

```text
Windows: Explorer, Open with, the command line, a second launch
       │
       ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ Main process (Node.js)                                                     │
│   index.ts        lifecycle, single instance, custom protocols             │
│   AppController   which documents are open in tabs; the request queue      │
│   tab-registry    the tabs: their ids, their order, the one on screen      │
│   documents.ts    reads files, decodes text, enforces the size limit       │
│   settings-store  theme, zoom, update and tab choices in settings.json     │
│   session-store   the open tabs, kept in session.json                      │
│   updates.ts      when to check for a new version, what the page is told   │
│   policies        links, local paths, images, external URLs, IPC senders   │
└────────────────────────────────────────────────────────────────────────────┘
       ▲
       │ validated IPC, app://, mdreader-local://
       ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ Preload (sandboxed)                                                        │
│   exposes window.mdReader: 23 fixed functions, never ipcRenderer           │
└────────────────────────────────────────────────────────────────────────────┘
       ▲
       │ contextBridge
       ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ Renderer (React, no Node.js)                                               │
│   App: Toolbar, TabStrip, DocumentView (MarkdownRenderer), StatusBar       │
│   workspace: the tabs and what each shows; hooks: settings, shortcuts,     │
│   drop target, wheel zoom                                                  │
└────────────────────────────────────────────────────────────────────────────┘
```

## Source layout

| Folder           | Role                                                                                                                                                                                                                                                                                        |
| :--------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `src/main/`      | The main process. Plain modules with injected dependencies, so almost all of it is unit-tested without Electron. `index.ts` is the only file that wires Electron objects together.                                                                                                          |
| `src/preload/`   | One file: the bridge exposed to the page.                                                                                                                                                                                                                                                   |
| `src/renderer/`  | The React app. `markdown/` holds the rendering pipeline; `workspace.ts` the tabs and what each one shows; `hooks/` the React side of the state (settings, the workspace, shortcuts, drop target, wheel zoom); `components/` the UI; `styles/` plain CSS with design tokens for both themes. |
| `src/shared/`    | Code and types used by more than one process: the IPC contract (`ipc.ts`), settings, zoom, the Content Security Policy, text statistics, theme colours. No Electron or DOM imports.                                                                                                         |
| `build/`         | Application and document icons (SVG sources and generated `.ico`/`.png`) and `installer.nsh`, the extra installer script.                                                                                                                                                                   |
| `scripts/`       | Icon generation and the release tooling: version check, checksums, release verification (including the update files), and the installer test that runs on CI.                                                                                                                               |
| `tests/`, `e2e/` | Cross-cutting tests and the end-to-end tests. Unit tests sit next to the code they test (`*.test.ts`).                                                                                                                                                                                      |

## Processes

### Main process

- **Lifecycle (`index.ts`).** Takes the single-instance lock. A second launch hands its command line to the running instance (`second-instance` event) and exits. Registers the two custom schemes, shows the tabs of the last run (`restoreSession`) without reading them, builds the window, and waits for pending settings and session writes before quitting. The application menu is removed.
- **`AppController` and `TabRegistry`.** The window shows tabs, and the main process owns them. `TabRegistry` (`tab-registry.ts`, plain bookkeeping) holds the list: an id for each tab (`tab-1`, `tab-2`, never used twice), the document it shows, their order and which one is on screen. A document that already has a tab is shown in it instead of getting another, and there are at most 30. `AppController` decides what happens to the list. A file named at launch, by a second launch or by the operating system is held in an `OpenRequestQueue` (every request is kept) until the page reports it is listening, then opened in a tab of its own, one request after another in the order they were made (read side by side, the tabs would come in the order the disk happened to answer). Requests of the page's own may overlap: each gets its tab but only the newest takes the screen. Files are opened in two steps, all of them read first and then all of them given their tabs with nothing awaited in between, so that an answer cannot name a tab that moved on while the later files were being read; a file that cannot get a tab is not read. A link, Back or a reload names the tab it is for (the one the reader was looking at, which may no longer be the one on screen here) and acts on that tab; a newer one in the same tab, or the tab being closed, makes an older one give way (`canceled`), and a tab that is not open is `canceled` at once, with nothing read. The controller remembers the path of the tab a link is in, because links and local images are resolved and checked relative to it, and the paths of the documents it has shown, so that Back (`reopen`) accepts only those. A tab from an earlier session is read the first time as a link in a document is (`READ_CAREFULLY`: the link policy and the symbolic link checks, and a path to a network location is refused unread), until the user opens that file themselves or follows a link in the tab. Asking for the document of a tab (`loadTab`) while it is being read is answered by that read. Each change of the tabs is numbered (`TabsSnapshot.version`), sent to the page once (nothing is sent when nothing changed), and handed to the session store. It has no Electron dependency.
- **`documents.ts`.** Reads a file and returns an `OpenOutcome` (`opened`, `failed` or `canceled`). Every problem a user can meet (missing, a folder, wrong type, permission, locked, too large, invalid path) is a `failed` outcome with a message fit to display; nothing is thrown. The size limit is 5 MiB. `text-decoding.ts` decodes UTF-8 (with or without a byte-order mark), UTF-16 with a byte-order mark, and falls back to Windows-1252.
- **`settings-store.ts`.** `settings.json` in the user data folder holds the theme, the zoom level, two choices about updates (whether they are on, and whether the one-time explanation was read) and whether the tabs come back (`restoreTabs`). It is read synchronously once (the window needs it before it is created), written atomically (temporary file, then rename), serialized so the newest value always wins, and a damaged file falls back to defaults.
- **`session-store.ts`.** `session.json` in the user data folder holds the paths of the documents in the tabs and the place of the one on screen, so that the next run can open them again. Only the main process writes it, from its own list; the page can only switch the remembering off (`restoreTabs`, an ordinary setting), which removes the file and stops writing it. Changes are collected for 300 ms and written together, atomically and one write after another, and what is waiting is written before the app quits. `parseSession` reads it back as carefully as any input: only absolute paths of Markdown files on this computer (no NUL characters; a network location, a device path and an alternate data stream are dropped by the local path policy, while a drive letter that is a mapped share cannot be told from a local drive and is kept), at most 30, and a place that is no tab means the first; a file of more than 8 MiB is not read, and a damaged file means no tabs and is logged. A write that fails leaves no temporary file behind. No document is read at start. A restored tab is read when it first comes on screen.
- **Updates (`updates.ts`, `update-info.ts`, `request-timeout.ts`, `redirect-limit.ts`, `update-log.ts`, `updater-adapter.ts`, `update-environment.ts`).** `UpdateController` decides when to look for a new version (15 seconds after start, then every six hours, and 15 minutes after a check that failed; a download that fails is tried again after 15 minutes, then an hour, then six hours, so that a file that never arrives intact is not fetched every quarter of an hour for as long as the app is open; never while the user has it switched off, and switching it off stops whatever is under way on the network) and what the page is told (`UpdateState`, in `shared/updates.ts`). A check the user asks for within 30 seconds of one that found nothing, or within 5 seconds of one that failed, is answered with that result instead of a new request. A background check that fails is silent, because being offline is normal.
  The library never downloads by itself. When it announces a newer version, `update-info.ts` checks what the release offers: one installer file with a plain name (so it cannot point outside the release's folder or to another host) and a SHA-512, a plain version number that goes with the release's tag (`v` followed by the version), and nothing that asks for administrator rights or a web installer. Only then does the controller ask for the download. The controller uses the library only through a small port; `updater-adapter.ts` is the one file that uses the library's API (`index.ts` only hands it the library's updater object), and the library is compiled into the main bundle and not shipped as a dependency. The adapter also settles what the library would decide for itself: no automatic download, no web installer, no downgrade, and the random id of the installation that the library would send with every request (`x-user-staging-id`) replaced by a fixed word. `request-timeout.ts` gives up on a request that hears nothing for a minute, which neither Electron's network stack nor the library's own timer (it waits for an event that Electron never emits) would do. `redirect-limit.ts` ends a chain of more than ten redirects, which the library says it does but does not, and Electron never stops a loop by itself. `request-timeout.ts` also keeps hold of the requests that are under way, because that is the only way to stop a download: the library's cancellation fails the promise of a download and never aborts the request behind it, so the file would go on arriving. When the user switches updating off, the adapter cancels the download and aborts those requests. `update-log.ts` is the logger the library is given, and the one the controller writes its failures to: a small `update.log` in the profile folder (a packaged app has no console, so an update that did not arrive would otherwise leave no trace). It keeps itself under about 200 KB (trimmed atomically, counted in bytes), leaves out the installation's random id and the library's per-redirect chatter, turns control characters into spaces, looks only at the start of a long message, and never throws.
  `update-environment.ts` decides, from the build and the environment, whether this run may update at all: a development build never does; `MDREADER_UPDATES=off` disables it (the tests of the packaged app set it so that they never touch the network); the portable executable, recognised by the `PORTABLE_EXECUTABLE_FILE` variable its launcher sets, only reports a newer version; and only a development build may be pointed at a feed on this computer, which is how the end-to-end tests exercise the whole flow. Two more variables only move timing: `MDREADER_UPDATE_FIRST_CHECK_MS` (a packaged app honours it too) and `MDREADER_UPDATE_REQUEST_TIMEOUT_MS` (a development build with a feed only). A packaged app ignores every other variable: where updates come from is fixed in the package.
- **Link and path policy.** `link-resolution.ts` turns a clicked link into a Markdown file the app may open; `local-path-policy.ts` decides whether a path taken from document content may be touched at all; `symlink-policy.ts` finds where a file really is, part by part and without following links, so that a symbolic link or junction cannot lead to a network share; `external-links.ts` decides which URLs may leave the app; `certificates.ts` makes sure no client certificate is ever presented to a server; `renderer-location.ts` picks the page to load (a packaged app ignores `ELECTRON_RENDERER_URL`).

### Preload

`src/preload/index.ts` exposes `window.mdReader` with `contextBridge`. It is typed by `MdReaderApi` in `src/shared/ipc.ts` and consists of fixed functions: app info, get and update settings, the open dialog (one file or several), open dropped files, go back, in a tab, to a document that was already shown (`reopenDocument(tabId, path)`), open a link (`openLink(url, { tabId, newTab })`: in the tab it is in, or in a tab of its own), reload a tab (`reloadDocument(tabId)`), subscribe to documents opened from outside, five for the tabs (read them, switch, close, move, read the document of one) and a subscription to their changes, open an external link, open the Windows Default apps settings, close the window, and four for updating: read the update state, check now, restart into a downloaded update, and subscribe to changes of the state. None of them takes a version, a program or a path of the page's own choosing. The ones that take an address are checked again in the main process: a link as a link is (see Link and path policy), an external address by `external-links.ts`, and the path for Back against the documents that were shown. A tab is named by an id the main process issued, which the controller checks (an id it did not issue changes nothing, and nothing is read for it), and the paths of dropped files are read inside the preload script, from the `File` objects (`webUtils.getPathForFile`), which only a real drop can supply. The page names a file to open in two ways only: a drop, and a link. The preload script never hands out `ipcRenderer`.

### Renderer

- `App.tsx` composes the hooks and components. It renders nothing until the saved settings and the tabs have arrived, so a dark theme never flashes light and the start page never flashes before the tabs of the last run.
- `Workspace` (`workspace.ts`, plain logic without React) and its hook `useWorkspace` hold the tabs and what each one shows: the document it was last given, the history behind its Back, and where the reader was in it. The main process decides which tab is on screen and the page follows its numbered snapshots (a late one never replaces a newer one), so what is on screen and what links are resolved against are the same thing. A document that arrives for a tab is kept, also before the tab is announced. A tab that comes on screen without one is read with `loadTab` (the tabs of an earlier session start like that), unless the answer to a request of the page's own that may open a document (the Open dialog, a drop, a link in a tab of its own) is on its way, which is most likely the document; a link, Back or a reload in the tab it is in makes no tab wait. A tab never goes on showing a document that is not the one the main process says it has: when no request of the page's own is waiting, such a document is let go and the tab is read again. A link, Back and a reload name the tab the reader was looking at: `useWorkspace` keeps the id of the tab that was last drawn, which is not always the one the workspace has just heard about, because React draws changes as transitions and the reader can click in the old page meanwhile. Where the reader is in a tab is reported by the document view as they scroll (`onScrollTop`, only once they have acted on the document, and only for the document that is drawn, which each scroll request's token says) and given back when they return to the tab; the page's scroll position is never read at the moment a tab is left, when it may still be drawing another tab. A failed open never replaces what is on screen. Changes reach React as transitions, so a large document that is slow to render does not hold up the page.
- `TabStrip` is the row of tabs (the ARIA tab pattern, with the arrow keys, `Delete`, the middle button, and dragging to put a tab elsewhere), `TabUnavailable` is the page of a tab whose file cannot be read, and `SettingsMenu` is the gear with its popover, a native one that the browser opens and closes.
- `useUpdates` shows what the main process says about updating. `UpdateNotice` (under the toolbar, with or without a document open) and `UpdatesPanel` (a section of the start screen, so only while no document is open) are the only places it appears; the notice never takes focus, and release notes are never shown.
- `MarkdownRenderer` is described below. `DocumentView` owns the scroll container, wheel zoom and the word, line and reading-time statistics (counted with `Intl.Segmenter`, 200 words per minute).
- Styling is plain CSS in five files: `tokens.css` (the light and dark palettes, the fonts and the width of the reading column), `base.css`, `app.css` (layout and controls), `markdown.css` (the document) and `highlight.css`. `tests/contrast.test.ts` reads `tokens.css` and checks WCAG contrast for the text and interface colours of both themes.
- The type is the type Windows ships: Sitka Text for the body of a document, Bahnschrift for headings, Segoe UI Variable for controls and tables, and Cascadia Mono (Consolas where it is missing) for code and the marks in the margin. Nothing is downloaded or bundled, so the Content Security Policy, the package contents and `verify:release` are unchanged. The faces are tokens (`--font-reading`, `--font-display`, `--font-ui`, `--font-mono`), so bundling a font later changes one file.
- **The marks in the margin.** `markdown.css` draws the mark of the source before what it makes: `#` to `######` before headings, `>` before a quote, a code fence before a code block and `---` before a rule, each with a `::before` that hangs into the gutter of the column. They are small, in mono and in one warm tone (`--ghost`), and centred on the first line of what they mark (each heading sets its size and leading in `--size` and `--lead`, which the mark's position is computed from). Their alternative text is empty, so a screen reader does not say "hash hash"; they are not selectable; and below 720 px, when the gutter is too narrow to hold them, they are hidden. A code block does not scroll itself but its `code` does, because a scrolling box would clip a mark that hangs outside it. List items use the source's own `-` and numbers as their markers (`::marker`). `tests/margin-marks.test.ts` pins all of this.
- The start screen (`EmptyState`) carries the `markdown-body` class, so it is set in the same column and the same type as a document, with the same marks before its headings. Controls inside it keep the interface face.

## Opening a file

1. **At launch:** `findLaunchFile` (`cli.ts`) takes the first positional argument (skipping Chromium switches, resolving relative paths against the working directory, accepting `file:` URLs) and the controller queues it.
2. **Second launch:** the new process exits, the running one receives `second-instance`, brings its window to the front and queues the file. The files asked for from outside are opened one after the other, in the order they were asked for, each in a tab of its own, or in the tab that already has it.
3. **When the page is ready:** the page subscribes with `onDocumentOpened` and `onTabsChanged`, asks for the tabs with `getTabs`, and calls `notifyReady`; the queue delivers the pending requests; for each one the controller reads the file, gives it a tab, sends the document and then the tabs, in that order, so that the page already has the document when the tab appears.
4. **From the page** (Open dialog, drag and drop, link click, Back, reload) the same service answers through an IPC call. The dialog and a drop open several files at once, each in a tab, and announce the change once. A dropped file's path is read by the preload script from the `File` object and sent on; Back (`reopenDocument(tabId, path)`) names a tab and a document by path, and the main process accepts only a tab it issued and a path it has itself shown; a link carries the tab it was clicked in. In every case the main process validates what it is given again.

## Tabs and the last run

- **The page asks, the main process decides.** The page can switch to a tab, close it, move it and ask for its document, always by an id that the main process issued. An id it did not issue changes nothing, and a path is not an id. A link, Back and a reload name the tab they are for in the same way, and one that names a tab that is not open does nothing and reads nothing. Nothing else about the tabs can be set from the page.
- **Which tab is on screen is settled in one place.** The page does not switch tabs by itself: it asks, and shows the tab that the next snapshot names. The page can be a little behind, though (React draws a big document as a transition, and the reader can click in the old one meanwhile), so a link, Back and a reload say which tab they are for, and the main process resolves a link against the document of that tab and not of the one it has on screen.
- **At the next start.** `index.ts` loads `session.json` (unless `restoreTabs` is off, in which case the file is removed), hands the list to `restoreSession`, and the tabs exist before the window does. The page learns them from `getTabs`; the one on screen is read at once and each of the others when it is first shown. A file named on the command line is added after them and shown. A tab is read the first time as a link in a document is, so that a file that has become a link to a network share since the tabs were saved is refused and not contacted; a path that points at a network location is not even kept in `session.json`. A tab whose file cannot be read stays and says why, with **Try again** and **Close tab**; the file may be on a drive that is not connected yet.
- **Switching it off.** `restoreTabs` is an ordinary setting that the page may change. `onSettingsChanged` in `index.ts` tells the session store, which cancels what was waiting to be written and removes the file; switching it on again writes the tabs that are open at that moment.

## Custom protocols

- **`app://md-reader/`** serves the built renderer from `out/renderer`. A custom scheme gives the page a real origin for the Content Security Policy and means the page has no `file://` privileges. The handler allows `GET` only, decodes and resolves the path, and refuses anything outside the renderer folder.
- **`mdreader-local://image/?u=<file URL>`** serves the images a document references. The main process validates the request: the path must pass the local path policy, have an image extension (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, SVG), and be at most 25 MB. Responses carry `nosniff` and a restrictive CSP of their own.

In development, the page comes from the Vite dev server instead, and the Content Security Policy is relaxed only for what Vite needs.

## Markdown pipeline

`react-markdown` with these plugins, in this order (`src/renderer/markdown/pipeline.ts`):

1. `remark-gfm`: tables, task lists, strikethrough, autolinks, footnotes.
2. `rehype-raw`, only when the text contains something that looks like HTML. It parses inline HTML, which is the slowest step for large documents.
3. `rehype-sanitize` with GitHub's allow-list, with its URL schemes narrowed: links may be `http`, `https`, `mailto` and `file` (relative links become `file:` URLs); images may be `https`, `data` and `file`. `<picture>` and `<source>` are removed, because the addresses in a `srcset` would bypass the image checks (the `<img>` inside is kept).
4. Heading ids (`slugs.ts`), GitHub-style, shared across the pieces of a long document. They run after the sanitizer, which would otherwise prefix them.
5. `rehype-highlight` with `detect: false` and `ignoreMissing: true`: only languages named on the fence are highlighted. The set is highlight.js's common languages plus PowerShell, batch, Dockerfile, HTTP and nginx. Just before it, `highlight-limits.ts` takes the language off a block with a line over 1,000 characters or more than 200,000 characters in all, so it is shown as plain text: highlight.js takes time quadratic in the length of a line (minutes for a 200 KB line).

React components then take over the elements that need decisions: links (`links.ts` classifies a link as an anchor, an external URL, a local file or blocked; a click never navigates the page), images (`images.ts` chooses local, remote `https`, inline `data:` or blocked, and failed images become a text placeholder), tables (wrapped so wide ones scroll), and task-list checkboxes (display only).

### Long documents

The Markdown parser slows down more than linearly on documents with very many small blocks (a 1 MB changelog took 12 seconds in one piece), and it works in one uninterrupted stretch. `chunks.ts` therefore splits documents over 64 KiB into pieces of about 32 KiB, cutting only where the result cannot change: at the start of a heading or, in a long stretch without one, a paragraph; never inside a code fence, an HTML comment, a `<pre>` block or an open block-level HTML element such as `<details>`. Link reference definitions are repeated in every piece. A document with footnotes is never split, because footnotes are numbered across the whole text. `MarkdownRenderer` shows one piece per turn of the event loop, so the first screen appears at once and the window stays responsive; `onComplete` fires when the last piece is on screen, and only then are the scroll position restored, anchors followed and statistics counted.

### Hostile files

A few kilobytes can make a parser do enormous work: quotes nested thousands of levels deep (`> > > …`) cost time that grows with the square of the depth and overflow the stack, and a single 200 KB line of code takes highlight.js minutes. The 5 MiB limit does not help against costs like these, so there are three layers:

- `nesting.ts` looks at the start of every line and, if a document stacks more than 100 quote marks or list markers on one line or indents a line more than 400 columns, `MarkdownRenderer` shows the text as plain text with a notice instead of formatting it. Real documents never come near these limits.
- The costs that remain are kept linear: the patterns in `chunks.ts` cannot rescan a line from every `<`, and only a bounded amount of link definitions is repeated into each piece.
- Every piece of a document is drawn inside a `RenderBoundary`, so if the parser still throws, a message replaces that piece and the rest is shown. The whole app sits in another boundary that shows `CrashNotice` with a Reload button, so a failure can never leave a blank window with no way out.

The `app://` and `mdreader-local://` handlers, the CSP and the IPC handlers each have unit tests, and the end-to-end suite checks the result in the real app: hostile HTML is stripped and the page stays intact, inline script and `eval` are blocked by the CSP, and no network request is made while a document is shown. The update flow is exercised end to end in a development build against a feed served from the test itself: a newer version is found, downloaded and checked; no identifier of the installation is sent; a download whose hash does not match, and an offer that asks for administrator rights, are refused; a feed that stops answering is given up on and works again afterwards; a feed that redirects for ever is cut off after ten redirects; a download that is under way when updating is switched off is stopped, which the test's server sees as a connection that closed early; the app looks by itself after a start, and stops when switched off; a feed with nothing newer says so; the switch persists; and a test feed can never run what it downloads. In a packaged app, one test sends every request to a proxy that refuses it and checks that the check fails cleanly, says so, and is written to `update.log`: that is the only automated run of the bundled library and the package's own update configuration, and it cannot reach GitHub.

## Windows integration

- **Identity.** `app.setAppUserModelId('io.github.abhijithkm.mdreader')` equals the `appId` in `electron-builder.yml`, so taskbar grouping and the installer's shortcuts agree (`tests/builder-config.test.ts` guards this).
- **File types.** `fileAssociations` in `electron-builder.yml` makes the NSIS installer register the ProgIDs `MDReader.md` and `MDReader.markdown` (description "Markdown Document", the document icon, and an open command) and point `.md` and `.markdown` at them. `build/installer.nsh` adds the "Open with" registration (`Applications\MDReader.exe`) and the Settings > Default apps entry (`Software\AbhijithKM\MDReader\Capabilities` plus a `RegisteredApplications` value named `AbhijithKM.MDReader`; both carry the publisher name so that uninstalling cannot remove another program's entries), and writes the open commands again with the program path in quotes (electron-builder leaves it unquoted, which is ambiguous when the user's profile folder has a space in its name). All of it is under `HKEY_CURRENT_USER`, because the install is per user.
- **What the installer does not do.** It never writes Windows' protected `UserChoice` key, so it cannot override a program the user has already chosen for `.md` or `.markdown`; that choice is made in Settings. Where nobody has chosen, the per-user registration above is what makes MD Reader open the type. Both facts are explained to users in the README. Electron's `app.setAsDefaultProtocolClient` is not used: it is for URL protocols, not file extensions.
- **Updating.** The installer is per user, so an update needs no elevation. The app downloads a newer installer in the background and runs it silently when the app closes (or at once on **Restart now**); the installer upgrades in place and the new version registers everything again. `build/installer.nsh` keeps the copy of the installer that electron-builder stores in `%LOCALAPPDATA%\md-reader-updater`, because the updater compares the next version with it and downloads only what changed. The updater also keeps the last installer it downloaded in a `pending` folder there until the next update replaces it, so the folder holds up to about 200 MB. The new installer runs from that folder with `--updated /S`, after it has uninstalled the old version, and that uninstall must not delete the folder its own installer sits in: the `isUpdated` guard in `installer.nsh` sees to it, and `scripts/installer-test.ps1` runs an installer from there to check it. The installer runs silently after the app has quit and takes a few seconds; if Windows is shut down in that time the installation can be left half done, and the installer from the release page puts it right. This is accepted: installing while the app runs would mean replacing files that are in use.
- **Uninstall.** Removes the ProgIDs, the "Open with" and capability registrations, the shortcuts, the updater's folder and the program. It clears the `.md` and `.markdown` defaults only if they are still MD Reader's, and neither it nor the updater's folder is touched during an upgrade (the new installer runs from inside that folder). User settings in `%APPDATA%\MD Reader` are kept.
- **Run as the user.** Both executables request `asInvoker`; nothing asks for elevation. `scripts/verify-release.mjs` reads this from the manifests of the built files.

## Build and packaging

- `electron-vite` builds three targets into `out/`: main and preload as CommonJS (a sandboxed preload must be CommonJS) and the renderer as a Vite bundle.
- `electron-builder` packs `out/**` and `package.json` into `app.asar` (the archive holds six files: the three compiled bundles, the renderer's stylesheet and page, and `package.json`; `scripts/verify-release.mjs` fails the build if anything else, such as source, tests, dependencies or source maps, gets in), keeps only the `en-US` Chromium locale, and builds the NSIS installer and the portable executable for x64. `publish` names this GitHub repository, which makes electron-builder write `resources/app-update.yml` (where an installed copy looks for updates) and, next to the installer, `latest.yml` and the installer's `.blockmap`. Every build runs with `--publish never`, so electron-builder never uploads anything; the release workflow attaches the files, and `scripts/verify-release.mjs` checks that they agree with the installer.
- Version information, the icon and the fuses are written into the executable at packaging time. No code-signing certificate is configured, so the output is unsigned.

## Decisions worth knowing

- **A custom scheme instead of `file://`** for the page, so the CSP has a real origin and the page has no file privileges.
- **Chunked rendering instead of a worker or virtualization**: it keeps the plain DOM (so find-in-page, text selection and anchors work as in a browser) while bounding the cost of any single step.
- **One window, several tabs, and the main process owns the tabs.** A list of tabs kept by the page would have to be believed by the main process, and a page that a hostile document has taken over could use that to name files. With the list in the main process, the page asks for a change to a tab it was given an id for, and it still names a file only through a drop or a link, both of which are checked. The cost is a numbered message to the page for every change, and the page keeping the documents. Tabs cannot be moved out into windows of their own, which would need a second window to keep consistent.
- **What is remembered is a list of paths.** The tabs come back because MD Reader keeps the full path of each open file and which tab was on screen, and nothing of what the documents say. The README tells the user, the setting is in the toolbar and not buried, and switching it off deletes the file. A restored tab is read only when it is first shown: reading thirty files at start would slow it and fail for the ones that are gone. A path on a network location is not remembered at all, because reading it at start would make Windows send the reader's credentials to that server when nobody had asked, and a remembered file is read the first time with the checks for links, because a file that was an ordinary one when it was saved can have become a link to a share since.
- **Updates are on by default, and the page has no part in them.** The installed app updates itself, because a reader that is installed once and forgotten should not stay on a version with a known flaw. The cost is that the app now contacts GitHub, so the README says so, the first run explains it, and one button turns it off. There is still no telemetry and no account. The portable executable only reports a newer version, because a program cannot replace the file it runs from.
- **An offer is looked at before it is downloaded.** The library would download whatever `latest.yml` names, including a file path that leaves the release, a request for administrator rights or a web installer that fetches more. The app asks it not to download by itself, checks the offer, and only then asks. An offer that fails the check is ignored and logged, and nothing is half-installed.
- **The request timeout, the redirect limit and the cancellation are ours, and were tried on the real stack.** A first version of the timeout trusted Electron's documentation about when a request is over, and never fired, because Electron says `close` as soon as a request has been sent. What ends the watch is now the response's own events, an error, and the library's call to abort. Throwaway probes on Electron's real network stack, with the real library, checked a silent server, a download that trickles in for longer than the limit, one that stalls, the same behind a redirect, and a redirect loop. `e2e/updates.e2e.test.ts` keeps three of these as regression tests (a silent server, a redirect loop, and a download stopped half way when updating is switched off); the trickling and stalling downloads are covered in `request-timeout.test.ts` with a fake request, and by the probes only.
- **Switching updating off stops what is under way.** Someone who turned updating off does not want a download to carry on, least of all on a metered connection, and the library's own cancellation does not stop one (it only fails the promise). Anything the library then reports about what it was doing is ignored and only logged, so that the switch is left as the user set it.
- **A download that keeps failing is tried less and less often**: after 15 minutes, an hour, and then with the checks every six hours. A file that never arrives intact (a proxy that cuts it short, a bad copy at the far end) would otherwise be fetched, about 100 MB at a time, every quarter of an hour.
- **The Updates section is on the start screen only.** A section in the document view would take room from reading. The cost is that someone who only ever opens documents from Explorer sees the one-time explanation and the notice that an update is ready, but has to start MD Reader without a document to check by hand or to change the setting. This is a choice to revisit before 1.1.0 is final (a menu or a shortcut would fix it).
- **The update library is compiled into the app.** It is a development dependency that the build bundles into the main process, so the package still holds only compiled code and `verify:release` can keep refusing anything in `node_modules`.
- **Updates install when the app closes.** A reader should never restart under someone who is reading; **Restart now** is there for people who want it at once.
- **Settings are four values.** A bigger store would need migrations; four validated fields, with a default for any that an older file lacks, do not.
