# Testing

MD Reader is tested at several levels. All but the last run automatically; the last is a checklist for a person on a real Windows machine.

| Level                                                                | Command                                                     | What it shows                                                                                    | Runs on                                       |
| :------------------------------------------------------------------- | :---------------------------------------------------------- | :----------------------------------------------------------------------------------------------- | :-------------------------------------------- |
| Static checks                                                        | `npm run lint`, `npm run typecheck`, `npm run format:check` | Strict TypeScript, ESLint (type-aware), consistent formatting                                    | local, CI                                     |
| Unit and integration tests                                           | `npm test`                                                  | Every module and React component, the build configuration, the release scripts and the workflows | local, CI                                     |
| End-to-end tests                                                     | `npm run test:e2e`                                          | The real Electron app, driven over the Chrome DevTools Protocol with Playwright                  | local, CI                                     |
| The same end-to-end tests against the packaged and the installed app | `MDREADER_EXE=<path to MDReader.exe>`                       | That what users get starts and behaves like the development build                                | local (packaged), CI (packaged and installed) |
| Installer test                                                       | `scripts/installer-test.ps1`                                | A real install, upgrade and uninstall, and the registry and shortcuts they leave                 | CI only (see below)                           |
| Portable smoke test                                                  | `scripts/portable-smoke.ps1 -Portable <exe>`                | The portable executable starts and opens a document named on the command line                    | local, CI                                     |
| Manual checklist                                                     | [below](#manual-windows-test-checklist)                     | What automation cannot see: Explorer, Settings, SmartScreen, scaling, assistive technology       | a person                                      |

## Running the tests

```bash
npm run check          # lint, typecheck, unit tests and build
npm test               # unit and integration tests only
npm run test:e2e       # end-to-end tests against the development build
```

The end-to-end tests launch the application through the installed Electron, so they need `npm run build` first, and Electron must be downloaded (`npm run dev` does that on first use, or run `npx install-electron`). To run them against a packaged build instead, point `MDREADER_EXE` at it:

```powershell
npm run pack
$env:MDREADER_EXE = "$PWD\release\win-unpacked\MDReader.exe"
npm run test:e2e
```

Each test starts the app with its own empty profile folder (`--user-data-dir`), which also isolates the single-instance lock, so tests never touch your real settings or an MD Reader you have open. The test launcher also sets `MDREADER_UPDATES=off`, so the app never looks for updates on the internet during a test. Two files turn updating on. `e2e/updates.e2e.test.ts` does it in a development build, against a feed that the test serves itself on this computer, and in a packaged app with every request sent to a proxy that refuses it, so that nothing outside is reached. `e2e/screenshots.e2e.test.ts` does it only to show the Updates section, and puts the first check a day away. Every CI step that runs the end-to-end tests runs them against a packaged app, which never honours a feed, so CI has a step of its own for the feed tests (`npm run test:e2e -- updates`, after the build).

Three more variables exist for these tests, and none can send an installed app anywhere: `MDREADER_UPDATE_FEED` (the feed; development build only, and only an `http://` address on this computer, that is `127.0.0.1`, `localhost` or `[::1]`, with a port and any path), `MDREADER_UPDATE_FIRST_CHECK_MS` (how long after start the first check waits, up to a day; a packaged app honours it too, as it only moves a check that was coming anyway) and `MDREADER_UPDATE_REQUEST_TIMEOUT_MS` (how long a request may stay silent, from 100 ms to ten minutes; development build with a feed only). `MDREADER_EXE` must be a path when it is set: an empty value is refused, because a workflow step that found no path would otherwise start the development build and pass.

To regenerate the README screenshots from the real app, in PowerShell: `$env:MDREADER_SCREENSHOTS = '1'; npm run test:e2e -- screenshots`. Point `MDREADER_EXE` at a packaged build first (see above) if the start screen is to show the Updates section: a development build cannot update, so it has none.

## The installer test (CI only)

`scripts/installer-test.ps1` runs in the Release workflow on a fresh Windows runner:

1. **Install:** installs an older build (version 0.0.1, built for this purpose), then installs the new version over it, silently. It then checks that there is exactly one MD Reader entry in Apps & features with the new version; that it is installed under the user's profile; that `MDReader.exe`, the uninstaller and the application archive exist; that the Start menu and Desktop shortcuts exist and point at the program; that `.md` and `.markdown` are registered to `MDReader.md` and `MDReader.markdown`, with an open command that uses the installed program, and an icon that exists; and that the "Open with" and Settings > Default apps registrations are present; and that the copy of the installer that updates compare with is kept in `%LOCALAPPDATA%\md-reader-updater`.
   It then installs the new version once more the way the app's own updater does: the installer is run from `%LOCALAPPDATA%\md-reader-updater\pending` with `--updated /S`. The old version is uninstalled first, and that must leave the folder alone, because the installer that is running sits in it (`build/installer.nsh` takes care of that). The script checks that the installation is intact and that what the updater keeps in that folder is still there. No other test runs an installer from that folder. Of these checks, the one that fails when the guard is missing is the one for the note that the script put in that folder: an uninstall that removed the folder would take the note with it. That the installer which is running is still there proves little, because Windows will not delete a program while it runs, and the other checks show that the installation is intact. This step is new, and has been checked by reading the script and by parsing it, but has not yet run on a runner.
2. The workflow then runs the **end-to-end tests against the installed program**.
3. **Uninstall:** runs the installed uninstaller and checks that the program, the shortcuts and every registration are gone, that the `.md` and `.markdown` defaults no longer point at MD Reader, that the updater's folder is gone, and that the user's data folder is kept.

The script changes the current user's file associations, so it refuses to run unless the `CI` environment variable is `true` (or `-AllowLocal` is passed). It is not run on development machines. To try it yourself, use a disposable Windows 10/11 virtual machine or a spare user account, never your main account:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\installer-test.ps1 -Phase Install -Installer release\MDReader-Setup-1.0.0.exe -AllowLocal
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\installer-test.ps1 -Phase Uninstall -AllowLocal
```

## Manual Windows test checklist

Run this on a clean Windows 10 or 11 machine (a virtual machine is ideal) before the first release, and again after any change to the installer, the file association registration, or how files are opened. Use a standard (non-administrator) user for the install steps. Note the Windows build and the MD Reader version you tested.

### Preparation

- [ ] Get the installer from the release (or the workflow artifact) and check its hash: `Get-FileHash -Algorithm SHA256 .\MDReader-Setup-<version>.exe` equals the line in `SHA256SUMS.txt`.
- [ ] Prepare test files in a folder whose name has spaces, for example `C:\Test Docs\`:
  - `Ünïcode ファイル.md`, a short document with Unicode text;
  - `sample.md` (copy `docs/sample.md`), plus `other.md` and an `images` folder with `pic.png`, with `sample.md` linking to `other.md` and showing `images/pic.png` and `../pic.png`;
  - `notes.markdown`, a UTF-16 file saved from Notepad, and a plain `readme.txt`;
  - `big.md` of about 2 MB: `1..60000 | ForEach-Object { "- item $_ with some **bold** text" } | Set-Content big.md`, and a file over 5 MB.

### Install

- [ ] Run the installer. There is no administrator prompt. SmartScreen shows its warning once; **More info > Run anyway** lets it continue.
- [ ] MD Reader starts when the installer finishes. A Start menu and a Desktop shortcut exist.
- [ ] Settings > Apps > Installed apps lists "MD Reader" with the right version, once.
- [ ] The program is under `%LOCALAPPDATA%\Programs`.

### Opening files

- [ ] **Ctrl+O** shows the Open dialog filtered to Markdown files; open `Ünïcode ファイル.md`.
- [ ] Right-click a `.md` file > Open with: MD Reader is in the list (Choose another app if needed) and opens the file.
- [ ] Settings > Apps > Default apps: search `.md`, choose MD Reader; do the same for `.markdown`. Both file types now show the MD Reader document icon in Explorer (restart Explorer if the icon is stale).
- [ ] Double-click `sample.md` in Explorer: it opens in MD Reader.
- [ ] With MD Reader open and showing `sample.md`, double-click `Ünïcode ファイル.md`: the same window gets a new tab for it, shows it, and comes to the front. Repeat with the window minimized. Double-click `sample.md` again: its tab is shown and no second tab appears.
- [ ] Drag a `.md` file from Explorer onto the window: a drop overlay appears, then the document opens. Drag `readme.txt`: a message explains it is not Markdown.
- [ ] From a command prompt in another folder: `MDReader.exe "C:\Test Docs\Ünïcode ファイル.md"` and with a relative path.
- [ ] If you can: open a file from a USB drive and from a network share. The document and its relative images load.
- [ ] Open the UTF-16 file and `notes.markdown`: text is readable.

### Rendering and links

- [ ] `sample.md`: headings, task list (checked and unchecked), numbered and bulleted lists, the table, both code blocks highlighted, the block quote, the horizontal rule, the footnote, the collapsible section.
- [ ] Both images show. Rename `pic.png` and press F5: a "not found" placeholder appears and nothing else breaks.
- [ ] Click the link to `other.md`: it opens in the same window. **Alt+Left** returns to `sample.md` at the same scroll position. A `#heading` link scrolls.
- [ ] Click an `https://` link: it opens in the default browser, not in MD Reader. A `mailto:` link opens the mail program.
- [ ] A document with `<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, `<iframe src="https://example.com">` and `[x](javascript:alert(1))`: nothing runs, no dialog appears, the page is intact and the unsafe link is plain text.
- [ ] A link to `file:///C:/Windows/System32/cmd.exe`, to `\\server\share\x.md` and to `readme.txt`: refused with a message; nothing launches.
- [ ] `big.md` stays responsive (you can scroll and zoom while it finishes). The file over 5 MB is refused with a message that names its size.
- [ ] A document that is one line of `> ` repeated 5,000 times: it appears at once as plain text with a notice about nesting, and the window stays responsive. A code block with a single 5,000-character line appears at once without colours.
- [ ] Drag a `.md` file from a network share (`\\server\share`) onto the window: it opens, because dropping it is your choice. A link inside a document to a file on a _different_ share is refused.

### Tabs

- [ ] Open three files (choose them together in the Open dialog with Ctrl+click, or double-click them one after the other): three tabs, the last on screen. Click each tab, use **Ctrl+Tab** and **Ctrl+Shift+Tab**, and the arrow keys with a tab focused. Scroll each document to a different place and switch back and forth: each keeps its place.
- [ ] Drag a tab left and right: a line shows where it will land, and it stays there. **Ctrl+Shift+Page Up** and **Page Down** do the same.
- [ ] Close a tab with its cross, with the middle button, with **Delete** on a focused tab and with **Ctrl+W**: the tab next to it comes on screen. Close the last one with **Ctrl+W**: the window closes.
- [ ] Two files with the same name in different folders (two `README.md`, say): both tabs show their folder.
- [ ] Open 30 files, then one more: a message says to close a tab. A file that is already open is still shown.
- [ ] **Ctrl**+click a link to another Markdown file, then middle-click one: each opens in a tab of its own, and the first tab is unchanged. A click without **Ctrl** follows the link in the same tab, and **Alt+Left** goes back in that tab only.
- [ ] Drop several `.md` files on the window at once: each gets a tab.
- [ ] Close the window with three tabs open and the second on screen, then start MD Reader again from the Start menu: the three tabs are back, the second is on screen, and the others are read as you click them. Delete the file of one tab before starting: that tab says it could not be found, and **Try again** and **Close tab** work.
- [ ] Open a file from a network share (`\\server\share\notes.md`) next to two local files, close the window and start again: the two local tabs are back, the one from the share is not, and `session.json` does not hold its path.
- [ ] The gear in the toolbar: **Reopen tabs when MD Reader starts** is on. Switch it off, close and start again: the start screen, no tabs, and `session.json` is gone from `%APPDATA%\MD Reader`. Switch it on again with a file open: `session.json` is there again.

### Upgrade and uninstall

- [ ] Install the previous release (or an older build), set the theme and zoom, then run the new installer. There is still one entry in Apps & features, with the new version; the theme and zoom are kept; double-clicking `.md` still opens MD Reader.
- [ ] Uninstall from Settings > Apps. The program and both shortcuts are gone. Double-clicking a `.md` file now asks which program to use. `%APPDATA%\MD Reader` is still there (delete it by hand for a clean slate).

### Updates

- [ ] With nothing open, the start screen has an **Updates** section that shows the version and says automatic updates are on. **Check for updates** ends in "is up to date" (or finds a newer version, if the release page has one).
- [ ] Close the app, delete `%APPDATA%\MD Reader\settings.json`, start it: a notice explains the check once, with **OK** and **Turn off**. **OK** hides it for good (restart to see that it does not return); starting again with **Turn off** leaves "Automatic updates are off" on the start screen.
- [ ] **The real update, with two pre-releases** (this is the only way to try the whole path): release `X.Y.Z-beta.1` and install it from the release. Release `X.Y.Z-beta.2`. In the running beta.1, press **Check for updates**: a notice says beta.2 is ready. (Left alone, the first check happens about 15 seconds after the app starts, and later ones every six hours, so a beta.1 that was started before beta.2 existed finds it at the next check.) Close the app and start it again: beta.2 runs, your theme and zoom are kept, Apps & features lists one MD Reader with the new version, and double-clicking `.md` still opens it. A copy that is not a pre-release never sees a pre-release.
- [ ] If it does not update, read `%APPDATA%\MD Reader\update.log` in the copy that should have: it records each check, the version found, the download and the reason for any failure.
- [ ] After that update, look in `%LOCALAPPDATA%\md-reader-updater`: `installer.exe` is the beta.2 installer again, and `pending` holds the one that was downloaded. With a firewall or proxy log, the download of beta.2 is much smaller than the installer, because only the blocks that changed are fetched.
- [ ] **Restart now** (needs a third pre-release, `X.Y.Z-beta.3`): in a beta.2 that shows the notice, press it. The app closes and comes back as beta.3, and no installer window shows.
- [ ] Switch automatic updates off, close and reopen: still off. With a firewall or proxy log, check that MD Reader makes no request to github.com while it is off.
- [ ] With a downloaded update waiting, switch updates off and close the app at once: nothing is installed, and the next start is still the old version.
- [ ] Disconnect from the network: no error and no notice appears at start; **Check for updates** says it could not check.
- [ ] Uninstall: `%LOCALAPPDATA%\md-reader-updater` is gone.

## What cannot be automated here

- SmartScreen and Explorer's behaviour, the Settings app, icon caches, scaling and contrast themes, and assistive technology: the manual checklist covers these.
- Installing on the machine that develops the app: see above. The installer test on CI is the automated substitute.
- Updating a real installed copy from a real GitHub release. The update flow is tested against a feed served by the test (in a development build, on Electron's real network stack: a server that goes silent, a redirect loop, a download stopped half way), the installer's side of an update (run from the updater's folder with `--updated /S`) by the installer test, and the start of a check by the packaged app by one test with a proxy that refuses every request. But reading the list of releases and `latest.yml` from GitHub, downloading from it, the redirect to its file servers, downloading only the blocks that changed, and the silent install when the app closes can only be tried by releasing two pre-releases and updating one to the other (see the checklist above). Until then they are verified by reading, not by running.
- The GitHub workflows themselves can only be exercised by GitHub. Their structure is checked by `tests/workflows.test.ts`; the first real run is the dry run described in [RELEASING.md](RELEASING.md#dry-run).
